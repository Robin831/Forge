category: Added
- **A worker can no longer repoint its anvil's `origin`** - Git keeps remotes in the config file of the repository a worktree belongs to, never in the worktree, so `git remote set-url origin <path>` typed inside a worker writes the anvil's `.git/config` — for the daemon and for every other worker — and the value outlives the worktree, which is deleted at teardown. That is how an anvil came to point at `<anvil>/.workers/<bead>/.git` and spent a day with every fetch, dependency scan and PR reconcile failing against a directory that no longer existed. The mechanism is now measured rather than inferred, and the earlier reading was wrong in a load-bearing way: the write lands on the anvil with no `GIT_DIR` set at all, so it is a property of `git worktree` and not of the environment Forge exports into a worker. Nothing inside git prevents it — `GIT_DIR` confines refs, objects and the index and never config, and a value pinned in the anvil's `config.worktree` does not shadow a corrupted one, because git accumulates `remote.origin.url` across config files as a list rather than overriding — so Smith now puts a small `git` wrapper at the front of the agent's PATH, which is the one interception point that holds for every provider Forge can spawn. It refuses writes to the remote named `origin` (`remote add|remove|rename|set-url|set-branches`, `config remote.origin.url` and `.pushurl`, in git's old and 2.46 spellings, in any casing git folds to the same key — `remote.origin.URL` is the same key and `remote.ORIGIN.url` is a different remote — through `-C` and `-c` and an exported `GIT_DIR`) when they would land on a config file the current checkout does not own, and hands everything else to the real git untouched: every read of that same remote, every other remote name — a fork remote from `gh pr checkout` is unaffected — and every invocation that is neither `remote` nor `config`, which leaves the wrapper without a probe having been run. It fails open at each step it cannot answer, and it is on the agent's PATH and nothing else's, so the daemon's own git calls, the deployment's bootstrap and an operator's `git -C <anvil> remote set-url origin <url>` repair never meet it. `FORGE_DISABLE_GIT_GUARD` in the daemon's environment switches it off; a worker cannot set it for itself, and a guard that fails to install is logged and the agent runs with plain git rather than not at all. This is prevention of the accident, not a sandbox: an absolute path to git still walks past it, and on Windows it covers the agent's shell rather than a native child of it, since only a POSIX shell resolves an extensionless `git`.
- **The teardown check no longer explains the fault by `GIT_DIR`** - `CheckAnvilOrigin`'s account of how the remote gets written attributed it to the GIT_DIR Forge exports into a worker. It reproduces without one, so the comment named a cause that is not the cause and would have sent the next reader at the wrong file.
