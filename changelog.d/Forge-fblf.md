category: Changed
- **Epic orchestration is now opt-in** - Children of a parent bead dispatch as ordinary standalone beads (worktree from main, PR to main) unless the parent carries the new `crucible` label; an `epic-branch:<name>` label counts as opt-in too and still names the branch. `issue_type: epic` alone no longer routes children onto a feature branch, and a parent with children is no longer a Crucible candidate on that basis. Migration: add `crucible` to the parents that should keep being orchestrated. (Forge-fblf)
- **One source of truth for the epic branch name** - The poller derived `epic/<id>` while the Crucible built `feature/<id>`, so a child dispatched outside the Crucible failed with "base branch not found on origin" and burned its dispatch circuit breaker. Both now call `epic.BranchName`, which honours `epic-branch:<name>` in both places. (Forge-fblf)
- **Children of an orchestrating parent are no longer double-dispatched** - A parent that starts a Crucible — or is already running one — withholds its children from the same poll cycle's dispatch loop, instead of the loop and the Crucible each running them. (Forge-fblf)
- **A labeled parent with the Crucible disabled is escalated, not stalled** - `crucible_enabled: false` no longer creates a dangling epic branch and leaves the parent `in_progress` forever; the bead goes to Needs Attention naming both ways out, and its children are withheld from dispatch rather than each hard-failing on "base branch not found on origin" and burning its dispatch circuit breaker. (Forge-fblf)
- **An opted-in parent is never dispatched alone while its children still exist** - Its label is what routes the children, so a standalone dispatch merges the parent to main while they keep pointing at a branch nobody creates. "No children" is now asked of bd rather than read off the poll batch, where a child blocked on something else is indistinguishable from no child at all: only a parent whose children are all closed runs the ordinary pipeline, one with open-but-unready children is escalated naming them, and a schematic crucible check that declines an explicitly labeled parent escalates with its reason instead of routing the parent standalone. (Forge-fblf)
- **Label-supplied epic branch names are validated** - `epic-branch:<name>` values are screened against git's ref rules (`epic.ValidBranchName`) before being stamped onto children, handed to `git worktree add` or folded into a worktree path. A name that would be read as a flag (`epic-branch:--force`) or escape its directory (`epic-branch:../../x`) still opts the parent in, but falls back to the derived `feature/<parent-id>`. (Forge-fblf)
- **The Crucible guard escalates the parent that actually opted in** - With the Crucible off, a withheld child's stamp was attributed to its first parent candidate — and a `bd dep add` sequencing edge is `blocks`-typed, so an unrelated upstream task routinely comes first and was flagged `needs_human`, freezing ready work out of dispatch while the real parent was never escalated. The poller now records which candidate resolved the stamp, and the guard names nobody rather than guessing. (Forge-fblf)
- **Not included: auto-closing a grouping parent** - A parent whose children all closed in independent mode is still closed by hand; that follow-up is tracked as Forge-rjap. (Forge-fblf)
- **Fixed epic-branch resolution reading the dependency graph backwards** - `ResolveEpicBranches` read `Blocks` as "beads I block" after the poller had already overwritten it with "my children"; it now finds the parent through the child's `parent` field or a `blocks`/`parent-child` dependency entry. (Forge-fblf)
