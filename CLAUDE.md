# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build & Run

```bash
# Build
go build -o forge ./cmd/forge

# Build and run
go run ./cmd/forge

# Run tests
go test ./...

# Run a single package's tests
go test ./internal/pipeline/...

# Run with verbose output
go test -v ./internal/state/...

# Vet
go vet ./...
```

## Architecture

Forge is a **Go orchestrator daemon** that autonomously drives Claude Code agents across multiple git repositories. It uses a blacksmith metaphor throughout.

### Component Map

| Package | Role |
|---------|------|
| `internal/daemon` | Main background process. Runs the poll loop, manages IPC server, hot-reloads config |
| `internal/pipeline` | Orchestrates one bead through Schematic → Smith → Temper → Warden |
| `internal/smith` | Spawns `claude` CLI as a subprocess in a worktree |
| `internal/temper` | Runs build/lint/test checks; auto-detects Go, .NET, Node. Every step it detects carries a default `paths` glob set (`defaultGoPaths`/`defaultDotnetPaths`, `<dir>/**` for a Node subdirectory, nothing for a Node project at the root, which has no boundary to gate on), so changed-file gating applies on an anvil that configured nothing — gating had been reachable only by hand-writing `temper.steps`, which is why a one-line frontend change re-ran a whole .NET backend suite. Explicit `temper.steps` are untouched: a step written with no `paths` still runs unconditionally. The list those globs are matched against is nil by default, and nil means "unknown", which runs everything — so `ResolveBaseRef`/`ChangedFilesForBase` (`baseref.go`) are the one derivation of it that the pipeline, burnish and quench all call, rather than three that could gate the same diff differently. It fails open at every step: no base ref resolves → nil, git fails → nil, and `ChangedFilesOrNil` is that fail-open rule written once for the callers outside the pipeline (burnish and quench had a copy each) with `LogPathSkips` alongside it for the skip note. The Go set is the one that cannot be a static list: `go build` compiles whatever a package binds in with `//go:embed`, and those files share no extension, so `goStepPaths`/`goEmbedPaths` (`embedpaths.go`) scan the worktree for the directives themselves and gate on what they name — without it a PR touching only `internal/assay/prompts/*.md` skipped build, vet and test on Forge's own repo and reported PASS. A scan that cannot complete returns nil rather than a partial list, since a partial one reads as complete and the embeds it missed are exactly the ones that would skip the build — so an unreadable or oversized `.go` file aborts the scan instead of being dropped from it. Its one accepted exception is a non-regular entry: a symlinked `x.go` is skipped unopened, because `WalkDir` reports entries by `Lstat` (the size guard sees the link's own few bytes, not its target's) and the trees reaching this scan are not all Forge's own — quench and burnish verify contributor branches behind `ext-*` PRs, where `x.go -> /dev/zero` would read until the daemon is OOM-killed and `-> /dev/stdin` would block the verification goroutine forever. `ChangedFilesFromGit` passes `--no-renames` because a step is gated on the files a diff TOUCHES, not on the ones that survive it — rename detection reports a move as its destination alone, so moving the last file out of a gated directory looked like nothing happened there |
| `internal/warden` | Code review agent — validates Smith's diff, learns rules from Copilot comments |
| `internal/assay` | AI pull-request review engine ("Assay") — multi-pass PR diff review (Triage + Logic/Security/Conventions/Tests/Repo passes) with deduped, idempotent findings; triggered by Bellows on open PRs. A run where some deep passes reviewed the head and others did not is **partial**, not a failure and not a success: `DeriveStatus` (`status.go`) makes that three-way call once, and the result carries the pass tally plus a `PassFailure{Name, Reason}` per pass that never ran — the reason being the provider result subtype (`error_max_turns`) where there is one, which `PassError` keeps structured instead of leaving it to be re-parsed out of a message. Everything downstream reads that one computation: `assay_runs.status/completed_passes/total_passes/failed_passes` persist it, `RenderStatusText` renders `partial: 3 of 5 passes completed (failed: logic, repo-specific — error_max_turns)` into the daemon log, the `assay_partial` event message and the PR findings panel — the worker row itself carries only the status (the TUI's `◐` glyph, the web row's `partial` chip), not the tally — and `PartialCoverageNote` puts the same passes at the top of the PR summary comment — above the severity table, since a caveat read after the findings arrives too late. A partial run always posts a summary, findings or none: silence there is what would read as a clean review. The cheapest run is the one that never starts: after the incremental scoping and both diff filters, `shouldSkip` (`skip.go`) asks whether anything is left to review, and a diff with no `@@` hunk in it ends the run there — no triage, no five deep passes. The test is hunks and not an empty string because `FilterAutoGenerated` keeps the preamble ahead of the first block, so a lockfile-only push arrives as a few bytes of commit header that a length test reads as a diff and buys six sessions to review; the same test also catches a push that is nothing but renames, mode changes or binaries, none of which carry a line a finding could anchor to. Such a run is **complete** and carries `SkipReasonNoReviewableChanges` on `ReviewResult.SkippedReason`, which is the whole difference between it and a review that read the diff and found nothing — complete because the head has been dealt with and `LastReviewedSHA` must not re-dispatch it forever, while `CountAssayRuns` already excludes a row with a `skipped_reason` from the per-PR run cap. Every surface reads that field rather than the empty finding set: `assay_runs.skipped_reason` persists it, `StatusText` renders `skipped: no reviewable changes` instead of `complete: 0 of 0 passes completed`, `RunEvent.Message` puts it in the feed row where `0 findings` would otherwise sit, and `SkippedSummaryLine` replaces the PR comment's `no issues found` — the line that would report a review nobody ran as a clean bill of health. `PostRequest.SkippedReason` stops the same run at that summary: a skipped run posts no inline comment and, more to the point, counts no previously posted finding as missing, since two consecutive unreviewable pushes would otherwise age a live thread into auto-resolution on the strength of a run that read no code. A pass session also carries a **spend ceiling** (`assay.max_cost_per_pass_usd`, default $1.50, 0 disables): a provider prices a session only in its final result event, which is the moment the money is already gone, so `costTracker` (`cost.go`) adds up the per-turn usage the stream carries — `turnCostUSD` reads the `usage` block off each assistant event and prices it through `cost.EstimatePricing` (the non-logging twin of `FallbackPricing`, since an in-flight estimate is not a provider failing to report) — and cancels the session's context the moment the running total reaches the ceiling. What it bills is one API **message**, not one stream event: Claude emits an assistant event per content block, and a thinking + text + tool_use turn is three events repeating one `message.id` and one identical usage block (cache write included), so per-event billing charged a tool-using turn three times over and reached a $1.50 ceiling at a third of it — `costTracker.AddTurnCost` therefore takes the message id and ignores a repeat of one it has already billed (an empty id, from a backend that stamps none, keeps the per-event accounting since there is nothing to dedupe on). The estimate is an input/cache one by construction: the usage block is stamped when the message starts, so its `output_tokens` reads 2 or 3 however much the model then writes, which leaves the ceiling reading slightly low and never high. Ordering the outcome is `sessionOutcome` (`passes.go`), which asks the ceiling **first**: a killed session reports its death in whatever shape the kill produced — no result event, a non-zero exit, sometimes a rate-limit flag off the truncated stream — and classified further down it would come back `rate_limited` and be retried. The stop is its own reason, `ReasonMaxCost`/`error_max_cost`, never a flavour of `provider_failed`: the provider did nothing wrong, and nothing retries it — a re-run buys the identical runaway again at full price, which is why the max-turns retry branches on the reason rather than on a message. `costStopError` is the one place that decision is made, and its one exception is a session that answered anyway: the ceiling can only be crossed by a turn the model was already mid-answer on, so a completed answer is reported as the success it is rather than as a stop that did not happen. What the error carries is the tracker's own accounting (cost, turns, cache tokens), because a killed session emits no result event and `smith.Result` therefore reports zeros for a session the provider did bill — a stop is not a refund. It bounds a session rather than a whole pass: a strict-JSON re-prompt or a turn-budget retry each start with a fresh budget, and a backend that streams no per-turn usage (Gemini deltas, plain text) is never stopped on cost at all, since a ceiling that cannot see the spend must not become a source of failures. A pass that ends on `error_max_turns` is re-run **once** in a fresh session before it counts as failed (`maxTurnsRetries`, `runDeepPass` owns the loop and `runPassAttempt` knows nothing of it, so a retry cannot itself retry): that subtype means the model spent its budget exploring and never emitted JSON, not that it read the diff and found nothing, so only the final attempt's outcome is recorded — a pass that recovers is an ordinary success, never a residue in `PassErrors`. What the re-run must never be is the **same request again** (`retry.go`): a second session handed byte-identical inputs has exactly as much reason to spend its whole budget exploring as the first one did, so a pass failing this way cost about two sessions and routinely failed anyway — a partial run costing more than a complete one. `buildRetryMods` therefore modifies it three ways, each of which narrows the question rather than repeating it: a **halved turn budget** (`reducedTurnBudget`, floored at `minRetryTurns`=3, since a session cut below that cannot read the instruction, think and emit JSON), the appended **`answerNowInstruction`** telling the model to stop exploring and answer from what it already has, and — where the failed session's tool events named any — a **diff scoped to the changed files it actually opened** (`openedDiffFiles`, matched by path suffix because a provider reports absolute paths against a diff's repo-relative ones; only files already in the diff can be selected, so a path read from outside the change can never widen the scope). The budget rides on the context (`withTurnBudget`/`turnBudgetFrom`) for the same reason the stagger's release signal does — `PassRunner` is the one seam every stub implements — and the opened-file list rides out on `PassOutput.OpenedFiles` and, for the session that needs it, `PassError.OpenedFiles`, since a session that died on turns has no output to hang it on. The instruction is appended as a pure **suffix**, so everything above it is byte-identical to the first attempt and the retry still reads the shared prefix out of the provider's cache rather than paying to write it again. `planRetryInputs` is the mechanical enforcement: it hashes the assembled payload — prompt, diff and turn budget, length-prefixed so a field boundary cannot be shuffled across — and **refuses** a retry whose hash equals the original's, which is also what catches a modification that turns out to change nothing (a "reduced" budget equal to the original, a scoping `scopeDiffToFiles` declined because it would have emptied the diff). A refused or unconstructible retry is dropped outright: the pass reports its turn-budget failure as it stands and the run reports partial coverage, which is `passResult.retrySkipped` → `PassReport.RetrySkipped` → `retry=skipped` in `RenderPassTelemetry` — the one surface on which a re-run that was earned and not taken differs from a pass that was never eligible. A cost-ceiling stop never enters any of it: the loop branches on `ReasonMaxTurns`, and `ReasonMaxCost` has the opposite remedy. What the retry is tuned against is per-pass telemetry: the session's turn count rides through `PassOutput`/`PassError` onto `PassReport{Turns, TerminationReason, Attempts, Retried}`, and `RenderPassTelemetry` puts `pass=logic turns=12 term=error_max_turns retry=1` in the daemon's Assay log line as its own field — additive, so the coverage status text is untouched. Turns is a weak proxy for the question a coverage argument actually turns on, which is whether a pass read any code AT ALL: a pass terminating in one or two turns emitted its JSON without calling a tool, and over 20 logged runs that was the security pass's majority outcome (13 of 20, mean 2.5 turns) and repo-specific's on a third of them (7 of 20) — both reviewing diff text alone, which is how an endpoint missing the per-resource permission filter its siblings apply, and an unsynchronised dictionary reached from a parallel loop in another file, are each reviewed and each missed. The cause was the PROMPT and never the cap (the pass stopped voluntarily at 2 turns against a budget of 16): `prompts/security.md` closed with `Do not speculate about code you cannot see`, written against hallucination and read as an instruction to stay inside the diff, while `prompts/logic.md` carried no comparable clause and averaged 12.9 turns on the same budget. That clause now constrains the CLAIM and not the reading — open the implicated files and confirm before flagging — and both prompts name the one-hop work as expected rather than optional: the callers of a changed method, a sibling endpoint for this codebase's canonical authorization pattern, the construction and call sites of a service that gained a field, and for repo-specific the file each applicable checklist item concerns. `prompts_test.go` is the guard, because a regression in prose breaks nothing that compiles and surfaces only as silence. What makes the behaviour observable rather than inferred is `fileTracker` counting `tool_use` blocks alongside the paths it already recorded — counted separately, since a session that only grepped or ran a command names no file and folding the two would report it as one that never used a tool — riding through `PassOutput`/`PassError.ToolCalls` onto `PassReport{ToolCalls, FilesRead}` and rendered as `tools=9 files=4`, summed over the pass's sessions on `CostUSD`'s terms rather than `Turns`' final-session one, and omitted together when both are zero because a pass that used no tool and a backend that streams no structured tool events are one value there. That count is **not** the provider's `num_turns`, which is what made the first attempt to re-tune the budget from it impossible: `--max-turns` caps model MESSAGES (every one of 32 capped sessions had exactly the cap's 12 distinct assistant message ids), while Claude's `num_turns` reports tool-result rounds plus one on a session that answered — a message issuing three parallel tool calls is one turn and three rounds, which overstated 38% of successful sessions by up to 7 — and the constant cap+1 on one the budget killed, which says nothing at all. `turnCounter` (`turns.go`) therefore counts the distinct message ids off the stream, deduplicated for the same reason `costTracker.AddTurnCost` is (one API message arrives as an assistant event per content block), and `observedTurns` falls back to the provider's figure for a backend that stamps no ids — a field that cannot be derived degrades to the old number, never to zero. The budget the count is compared against is `assayMaxTurns` (16), and the number is auditable rather than guessed: `docs/assay-turn-budget.md` holds the distribution it came from, including why the logged p95/p99 of a censored sample cannot set it. Cost is counted the same way at both levels, because a failure is not a refund: `PassError.CostUSD` carries what a failed session was billed, and a run that returns no result at all — triage failed, or every deep pass did — leaves its spend on a `*RunError` wrapping the cause, which `assay.RunCost` reads back so the daemon records `assay_runs.cost_usd` on the error path exactly as on the success path. Every run closes itself out in the activity feed with **exactly one** terminal event — `assay_completed`, `assay_partial` or `assay_failed` — emitted from the one place a run ends (`emitAssayTerminalEvent`, `internal/daemon/assayevent.go`), so the `pr_review_needed` that opened the review always has a matching resolution: `Assay PR #347: complete — 5/5 passes, 7 findings ($2.80, 152s)`, rendered by `assay.RunEvent.Message` from the run record rather than the review result, since a run that died before the engine returned has no result but still has a record. A shadow-mode run appends `(shadow — findings in panel only)`: it posts nothing on the PR by design, so without the clause it was invisible end to end. A failed run names its cause (trimmed to one bounded line) instead of a findings count, which previously surfaced only as the worker row's state. Every prompt the engine builds is ordered **shared material first, and within that least-volatile first**: `writeSharedPromptHead` (`passes.go`) opens with `headStablePrefix` (`stable_prefix.go`) — which is `stablePrefix` (preamble, repo guidance, change context, already-reported findings) plus the incremental framing, the elided-file note and the diff — then the triage notes, and each pass's own instructions plus its JSON contract are appended AFTER it — `buildPassPrompt` and `buildTriagePrompt` both call that one function, since two builders assembling the same sections in the same order is precisely the arrangement that drifts by a newline and silently stops sharing. A prompt cache matches from the first byte, so the old order (pass instructions first) gave the five deep passes no common prefix at all and each re-wrote a byte-identical diff at full write price: 75.6% of every cache-write token Assay paid for was that redundancy. `TestDeepPassPromptsShareCachePrefix` is the guard — nothing pass-specific may move above the shared head. The volatility ordering inside the head is the same argument on the other axis: the shared head makes the five passes of ONE run share a prefix, `stablePrefix` is what makes a SECOND run of the same PR find that opening already cached rather than write it again, so its bytes may depend on the PR and the checkout and on nothing else. What that pushed below it: the incremental framing, because it names the baseline commit and so moves on every push — it now sits directly above the diff it describes rather than several kilobytes higher, where a push invalidated the already-reported list too. Those two tiers are two functions rather than one because they answer two questions: `stablePrefix` is what survives a PUSH, `headStablePrefix` is what survives a RE-REVIEW of the same head — and the second is the tier the money is in, since the diff lives in it. Below BOTH sit the triage notes, which are model-authored and therefore differ between two runs of the very same head. They used to sit between the framing and the diff, where they were the ceiling on every cross-run prefix: a re-review of one head matched only as far as the notes and then re-wrote a byte-identical diff at full write price in each of the five deep passes (on a 12 KB diff, moving them below cut a repeat run's cache-write tokens 55%, and the first deep pass of the re-run from 3,645 written / 1,536 read to 548 / 4,864). Below the diff they cost only themselves — but they also landed in the slot a reader is primed to treat as authoritative, immediately above the pass instructions, so `sharedPromptPreamble` names them a second time and `triageNotesSection` tags and fences them: machine-generated, advisory only, outranked by the final section. `TestSameHeadRerunReadsTheDiffFromCache` is the guard, `TestTriageNotesSitBelowTheDiff` names the boundary. The already-reported list is sorted into a total order by `sortedPriorFindings` — file, line, severity, title, then a digest of the whole record so no two entries can tie — and `maxPriorFindingsListed` is applied to THAT order: `pr_findings` is queried without an `ORDER BY`, so truncating what SQLite happened to return let two runs over one set list two different hundreds and rewrite everything behind the block. `TestStablePrefixIsByteStableAcrossRuns` is the guard for all of it. The scheduling half is the **staggered fan-out**: `deepPasses[primerPass]` (index 0, fixed so a replay staggers identically) runs alone until the provider emits its first model-output event, and only then are the other four released together — launched simultaneously they would all miss the cache and all pay to write the same prefix, which is what PR #5261 was observed doing with all five starting in the same millisecond. The signal rides on the context (`withFirstOutput`/`firstOutputFn`, `stagger.go`) rather than on `PassRunner`'s signature, and the smith runner turns it into a `SpawnOptions.OnStreamEvent` filtered by `isModelOutput` — Claude's opening `system`/init event is emitted before the model request is made, so releasing on "any event" would restore the race. The barrier fails open at every step: the gate is opened unconditionally when the primer *returns* (a primer that cannot spawn, is rate limited, or streams nothing has no token to give), `primerWaitDefault` (60s) bounds the wait regardless, and a run loses the cache saving rather than the four passes. The primer is a deep pass and never triage: triage is fed the FILTERED diff while the deep passes get the SCOPED one, so priming from triage would stop working the moment triage narrowed anything. Whether any of it is still working is visible only in telemetry, so `smith.Result.CacheCreationTokens`/`CacheReadTokens` (the provider's `cache_creation_input_tokens`/`cache_read_input_tokens`) ride through `PassOutput`/`PassError` — a failed session is billed for its cache write too — onto `PassReport{CacheCreationTokens, CacheReadTokens, Primer}`, and `RenderPassTelemetry` adds `cache_w=900 cache_r=41500` per pass plus `primer=1`, omitted together for a backend that reports neither. The per-run redundancy is the sum of `cache_w` minus the largest single one, which `ReviewResult.RedundantCacheWriteTokens` folds once for the daemon's `cache_w_redundant` log field rather than leaving whoever reads the line to re-derive it. The run-level totals ride out on `ReviewResult.CacheCreationTokens`/`CacheReadTokens` — accumulated exactly as `CostUSD` is, and carried on `*RunError` (`RunCacheTokens`) for a run that died, since the sessions a failed run made were billed for the prefixes they wrote — and the daemon persists them as `assay_runs.cache_creation_tokens`/`cache_read_tokens` on the success and the error path alike. Persisted rather than only logged because the question they answer spans runs of ONE PR and is therefore a query, not a line: a second run of the same PR should READ the opening its predecessor wrote. A zero there is ambiguous by construction — a pre-migration row, a backend that reports no cache accounting, and a run that genuinely shared nothing are one value — so a comparison is bounded rather than read as a regression. Whether any of it still holds end to end is `TestConsecutiveRunsReadTheStablePrefixFromCache` (`replay_test.go`), which drives two consecutive runs of one PR — the second a push later — through the real prompt builders against a stub provider emulating a prefix cache, and asserts on the second run's OPENING session: every later session reads what its own run's primer has just written, so "every pass reported a cache read" would pass with no cross-run sharing at all. Its floor is the stable region and its ceiling is the prompt (the new baseline and the new diff MUST be a miss), and the saving is measured against a replay of the identical run through an empty cache, so run 1's larger diff cannot flatter it. The companion case is the realistic one: run 1 reported a finding, so run 2's already-reported list differs and the hit stops there — everything above that list still shares, which is the whole reason the list is ordered last inside `stablePrefix`. Each session names itself: `PassLogPrefix` (`logname.go`) writes `assay-<runKey>-<pass>-<ts>-<seq>.log`, where the run key is the `ReviewRequest.LogKey` the daemon mints from the run's start time and also persists on `assay_runs.log_key`. One run writes six of those files, and before the key and the pass name were in them the bead Logs panel rendered a single review as six rows all reading `assay` — which reads as six runs, and so as six times the spend. The key is minted by the daemon rather than taken from the `assay_runs` id because the row is written when the run ENDS, long after every session has been named; it is all-digits and a pass name never is, which is what keeps the reader's parse able to tell the two apart and to keep recognising the older `assay-<ts>-<seq>.log` still on disk. `assay_runs.pass_findings` carries the per-pass findings counts off `ReviewResult.Passes` alongside it, since which of the six sessions mattered is not derivable from `pr_findings`, whose category is the model's to override. Every per-run surface above answers "what did THIS run cost"; `weekly.go` is the aggregate one, because a per-run figure is only legible against the runs around it — a 2.2x step change in the mean sat unnoticed for weeks while every individual line looked plausible. `WeeklyStatsFrom` folds `state.AssayRunSamplesSince` into **ISO** weeks (`WeeklyStats.Label`/`ISOWeekStart` — the last days of December belong to week 1 of the next ISO year, and any other calendar splits one week of spend across two rows), keyed by the run's completion time in UTC, and each week carries the split by outcome that the blended mean hides: the step change was a **partial** run costing more than a complete one, which is obvious only with the two printed side by side. `WeeklyStats.All` is FOLDED from the outcome buckets rather than accumulated beside them, so the headline mean is by construction the count-weighted blend of the splits rendered next to it. A skipped run is excluded at the query (it reviewed nothing and spent nothing); a failed one is not, since a failure is not a refund and spend shifting into failed runs is the very drift this exists to expose. `CostDrift` compares the current week's mean cost per run against the trailing four weeks **pooled** (total cost / total runs, so both sides of the ratio are the same quantity and a quiet week with three runs cannot outweigh a busy one with three hundred), flags past `DriftThreshold` (1.5x), and returns nothing below `MinDriftTrailingWeeks` (2) — one trailing week is one sample, which on a cold ledger would flag the second week of normal operation. Only weeks with runs become buckets: a synthesised zero-run week would enter that trailing mean as a 0.0 and read as a spend collapse — which is also why the check is handed `now` rather than reading the newest bucket as the current week: on a quiet week that bucket is a COMPLETED week some distance back, and comparing it against its own predecessors re-flags a step change that was reported when it happened, every day, for as long as the ledger stays silent. - **Short title** - Description of the change. (Forge-abc1)

**Rules:**
- **Line 1 MUST be `category: <Category>`** — one of: `Added`, `Changed`, `Fixed`, `Removed`, `Deprecated`, `Security`
- **Line 2+ are markdown bullet points** describing the change
- **Include the bead ID** in parentheses at the end of each bullet
- **Do NOT use commit-message style** (e.g. `fix: description`) — that format will break the changelog assembler

**Examples:**
```
category: Added
- **Ingot lifecycle tracking** - Track bead→PR→merge journey with structured test results in SQLite. (Forge-czem)
```

```
category: Fixed
- **Bellows CI status timing** - Only flag CI as failed when all checks are completed, not while still in progress. (Forge-68vu)
```

### Data Flow

```
bd ready (poller) → pipeline.Run()
  → worktree.Create (git worktree add)
  → [before_schematic hook] → schematic.Analyze (optional) → [after_schematic hook]
  → [before_smith hook] → smith.Spawn (claude CLI) → [after_smith hook]
  → deny_patterns validation (file globs + command globs, resets on violation)
  → [before_temper hook] → temper.Run (build/test/lint) → [after_temper hook]
  → [before_warden hook] → warden.Review (second claude session) → [after_warden hook]
  → if request_changes: loop back to Smith (max max_review_attempts iterations)
  → if approved: empty-branch guard — git rev-list --count <base>..<branch>
    → 0 commits (the work already landed on the base branch) → skip CreatePR,
      emit smith_empty_result, and resolve per settings.empty_diff_action
      (attention = Needs Attention entry, close = bd close with a note). Never
      retried and never counted against the dispatch circuit breaker: a
      re-dispatch would rebuild the identical empty branch. An unresolvable
      base ref or a failed rev-list falls through to the normal path.
  → if approved (branch has commits): vcs.Provider.CreatePR (gh pr create)
  → bellows monitors open PRs (CI fix, review fix, rebase)
    → Assay trigger gate → assay.Review (multi-pass AI PR review)
      → diff.* shapes the PR diff
        → nothing left to review (no hunks after the generated-file and
          skip_paths filters)? → record a skipped run (skipped_reason) and
          dispatch no passes; the PR summary says the review was skipped
      → Triage + parallel deep passes
      → dedupe/cap findings → post as PR review comments (idempotent per head SHA)
    → on merge: bd close with bounded retry (transient dolt errors — Error 1213
      serialization failures, i/o timeouts, lock timeouts — are retried)
      → still failing → persisted in `pending_bead_closes` + needs-attention
        ("merged but unclosed bead <ID> (PR #N) blocking M dependents")
      → every later bellows cycle re-derives the bead's status and re-attempts,
        clearing both once the close lands
      → close landed → maybeCloseGroupingParent: resolve the child's parent
        (poller.ParentCandidates) and close it when it is a plain grouping
        parent whose every child is now closed. Independent mode's counterpart
        to the Crucible closing an orchestrated parent after its final PR — so
        it is a no-op for a parent epic.IsOrchestrated says the Crucible owns,
        for an already-closed parent, and for one bd reports no children for at
        all. At most one parent per child close (no cascade to grandparents),
        and every bd failure leaves the parent open: it never changes what the
        merge close reports. Candidates are walked in order, but only until one
        of them turns out to BE this child's parent — it lists the child among
        its own children — after which the walk ends whether or not the close
        happened here: already closed, a sibling closing it right now (the
        parentAutoCloseInFlight guard's loser), an open sibling, a bd refusal,
        a candidate bd could not answer for at all. Only "this is somebody
        else's parent" continues, because ParentCandidates' trailing entries
        are `blocks` sequencing edges that merely look like parents from the
        child's side, and falling through to one closes a bead outside the
        relationship that justified acting. The one exception is an
        orchestrated candidate, which is skipped rather than terminal: the
        Crucible owning that bead says nothing about the next candidate. Child
        IDs reach a persisted close reason and the rendered activity feed, so
        they go through termtext.Line first
  → worktree.Remove

Crucible path (parent beads with children AND the `crucible` opt-in label):
  bd ready (poller) → detect bead.Blocks (children) + epic.IsOrchestrated(labels)
    → a child labeled `independent` is carved out of all of this: not stamped
      with the epic branch, not in the parent's Blocks, not withheld from the
      dispatch loop, not claimed by the Crucible, and not part of the epic's
      completeness set — its work reaches main through its own PR, so an open
      one never holds up the epic's final PR
    → children of an orchestrating parent are withheld from the dispatch loop
      (crucibleOwnedChildren) so one poll cycle never runs a child twice —
      the opt-in label is what makes a parent an owner, not crucible_enabled,
      so with the Crucible off the children are held back and the PARENT is
      escalated to Needs Attention rather than each child hard-failing on
      "base branch not found on origin" and burning its circuit breaker
    → everything that would dispatch the opted-in PARENT alone escalates it
      instead, because the label is what routes the children and a standalone
      dispatch cannot un-route them: the Crucible disabled, open-but-unready
      children (poller.OpenChildren — only all-closed/no children runs the
      ordinary pipeline; a bd error defers instead, so a flaky beads database
      never burns the dispatch circuit breaker), and a schematic crucible check
      that declines — the last one sanitized through termtext.Line, since the
      model's own text now reaches a persisted, rendered Needs Attention row
    → the first two describe a CONDITION, so they carry the `epic on hold: `
      prefix and clearResolvedEpicHold withdraws them the moment the parent is
      orchestrable again (Crucible on + a child ready). needs_human is sticky
      and those conditions are not, so without it a transiently-blocked child
      deadlocked the whole epic until an operator ran `forge queue clear`. A
      schematic decline carries no prefix: a label contradicting its own check
      is resolved by an operator, not by time
    → crucible.Run()
      → worktree.CreateEpicBranch (epic.BranchName: feature/<parent-id>, or epic-branch:<name>)
      → fetch children via bd show, topological sort
      → for each child: pipeline.Run() → vcs.CreatePR(base=feature branch) → vcs.MergePR
      → vcs.CreatePR(feature branch → main) — final PR
      → bellows monitors final PR (CI fix, review, merge → close parent)

depcheck.Monitor (background, weekly by default)
  → git fetch <upstream remote> <branch> — never a pull, so an anvil with
    permanently-modified tracked files is scanned and keeps them
  → reads go.mod / *.csproj / package.json out of that ref's blobs
  → scans each anvil for outdated dependencies (Go, .NET, Node), reconciling
    what the ecosystem tools report off the checkout against what the ref pins
  → npm half only: anvil has a live Kiln preview? → skip it this cycle (INFO,
    names the bead) — `npm ci` would delete the checkout's node_modules through
    the link the preview holds
  → creates beads for outdated dependencies (patch/minor auto-dispatch, major needs attention)
  → a git failure before the manifests are read is classified first:
    transient (DNS/timeout/connectivity/credentials) → depcheck_failed and a
    retry next run, exactly as before; blocked (detached HEAD, unlockable ref,
    tree mid-merge) → escalate ONCE into Needs Attention
    (AttentionKindDepcheck), then stay silent while the signature is unchanged.
    Cleared — and re-armed — by the next scan that reads the manifests

vulncheck.Monitor (background, daily by default)
  → runs govulncheck on Go anvils
  → creates prioritized beads for discovered vulnerabilities

logsweep.Monitor (background, daily by default)
  → deletes stale per-bead log dirs under ~/.forge/logs/<beadID>/
  → skips beads with a running worker; never touches the live daemon.log

Assay weekly cost report (background, daily; internal/daemon/assaycost.go)
  → folds assay_runs into the current ISO week plus the four behind it
  → one `Assay weekly cost` INFO line per week: run count, mean cost, mean
    duration, split complete vs partial (failed/unknown appended when non-empty)
  → `Assay weekly cost drift` WARN when the current week's mean cost per run
    exceeds the trailing four weeks' pooled mean by more than 1.5x
  → silent when the window holds no runs; `forge assay stats` is the same
    report on demand

anvilhealth check (once per FULL poll, per anvil; anvil_health_check)
  → SELECT `table`, num_conflicts FROM dolt_conflicts
  → non-empty → raise needs-attention (tables, count, ahead/behind), WARN, skip dispatch
  → empty     → clear the flag automatically (no operator action)
  → query error → state unknown: leave the previous flag untouched
```

### Two Front Ends: Hearth (TUI) vs Hearth 2.0 (web GUI)

Forge exposes the same daemon state through two independent front ends:

- **Hearth (TUI)** — `internal/hearth`, launched with `forge hearth`. A Bubbletea
  terminal dashboard that talks to the daemon over the IPC socket.
- **Hearth 2.0 (web GUI)** — `internal/web`, a chi HTTP server run **in-process**
  inside the daemon (no extra socket hop) and gated by `FORGE_WEB_ENABLED`. It
  dispatches to the same daemon command handlers the IPC layer uses, plus its own
  bcrypt-validated session login and SSE streams.

### State Database

`~/.forge/state.db` (SQLite with WAL mode) tracks:
- **workers** — Smith process lifecycle with PID, status, log path
- **prs** — Pull requests created across anvils. Three independent Bellows flags live on the row: `bellows_managed` (does Bellows run lifecycle workers for this PR at all — defaulted to 0 for `ext-*` PRs), `bellows_manually_assigned` (an operator pinned that answer, so the reconcile loop's defensive `ext-*` clobber leaves the row alone) and `bellows_detached` (managed, but **muted**: no events, no automatic quench/burnish/rebase/Assay dispatch, while mergeability and terminal state keep being refreshed). The detach flag is deliberately not folded into the other two — a mute is a different question from "is this PR ours" — and reconcile never touches it, so a detach survives the managed-flag rewrites. `UpdatePRBellowsDetached` is its only writer, behind the `detach_bellows` / `reattach_bellows` PR actions
- **events** — Timestamped event log (bead_claimed, smith_done, warden_pass, etc.)
- **retries** — Exponential backoff tracking; `needs_human=1` after exhausting retries
- **bead_costs / daily_costs** — Token usage and USD estimates per bead and per day
- **previews** — Kiln preview environments per bead: anvil, branch, status, worktree path, per-service JSON (name/port/health/pid/log, plus the started/exited timestamps and exit code a service that died after readiness carries), created/last-active timestamps
- **pending_bead_closes** — beads whose PR merged but whose `bd close` has not yet succeeded: PR number, close reason, cumulative attempts, last error, merge time. Re-attempted every Bellows cycle until the bead closes
- **review_fix_dispatches** — burnish dispatches per PR, keyed to the head SHA they ran against: head, attempts, last outcome (`pushed`/`unverified_push`/`preserved`/`failed`). The counter resets the moment the head moves, which is what separates a PR that is progressing from one rebuilding the identical diff every cycle; past `max_same_head_review_fixes` (default 2) the dispatch is refused with a Needs Attention entry instead. Fails open — an unreadable head SHA dispatches unchecked — and is cleared when the PR merges/closes or an operator runs `forge queue retry`
- **depcheck_failures** — anvils whose dependency scan is BLOCKED by a git condition that repeats every run: kind, the failure signature, the rendered title/detail, occurrence count, first/last seen. One row per anvil, and the signature is the whole suppression rule — a run whose signature matches the stored one records itself and stays silent. Cleared by the first scan that reads the anvil's manifests again, and pruned for anvils the config no longer registers (nothing else could withdraw those)
- **deploy_failures** — self-deploys that did not go live, keyed by anvil + reason (`drain_timeout`, `swap_failed`, `restart_failed`, `rollback_failed`): attempted/restored build SHAs, rollback flag, detail, time. Surfaced as anvil-level Needs Attention entries and cleared by the deployer once a later deploy supersedes them

| `preview_start` | Start a bead's preview environment. Payload: `ipc.PreviewActionPayload` — `bead_id` and `anvil` required, `branch` optional (defaults to `forge/<beadID>`). The bead id is a registry key: it is never looked up in bd, which is what lets `forge preview start kiln-smoke-1 --anvil <name> --branch main` preview a branch that has no bead. Answers `queued`; the tracked request completes with `ipc.PreviewStartResponse{bead_id, status, message, entry_url}`, of which `request_status` surfaces only `message` — a client wanting the URL reads it back from `preview_list`. |
| `preview_stop` | Tear a bead's preview down. Payload: `ipc.PreviewActionPayload` — `bead_id` required, anvil ignored. Answers `queued`; the tracked request completes with `ipc.PreviewStopResponse{stopped, bead_id, message}`. A bead with no live preview is rejected synchronously with `no preview running for bead <id>` (the automatic teardown paths call the manager directly, where stopping something already gone stays a no-op). |
| `previews` / `preview_list` | One command under two names — the dashboard's and the CLI's. No payload; answers `ipc.PreviewListResponse` (an alias of `ipc.PreviewsResponse`): live previews with per-service ports/health, each carrying `entry_url` (the operator-facing link, built by `kiln.EntryURL` from the settings: `https://<label>.<base>/` when `preview_proxy_base` routes by hostname, else the entry `port` on `preview_public_host` — which is what makes `forge preview list` print the same link the dashboard shows), the entry `port`, `idle_remaining_seconds` (null when the reaper is disabled) and a `resource_note` summarising the services/ports it holds; plus `preview_public_host` and `preview_idle_timeout` so clients build links and deadlines themselves, and `anvils` — the anvils a preview can be started for (previews enabled AND a `.forge/preview.yaml` in their main checkout), which is how a client gates a per-bead Preview affordance without a probe per row, plus `quest_anvils` — the anvils that also opted into `preview_quests`, which gates the "Run quests" action the same way. |
| `preview_resolve` | Resolve a preview host label to the address serving it, for `internal/web`'s host-based proxy. Payload: `ipc.PreviewResolvePayload` — `label` (required, `kiln.PreviewLabel` of a bead id) and an optional `service` from the `--<service>` form. Answers `ipc.PreviewResolveResponse`: `found` with `host`/`port` (the preview bind host, wildcard reported as loopback), or `found=false` with a reason from the `ipc.PreviewResolve*` set (`previews_disabled`, `no_preview`, `stopped`, `no_service`, `no_port`, `not_serving`) — a refusal is an `ok` response, since "that preview is not running" is an answer. `not_serving` is the one that is not about the preview's existence: it is up, and the process behind that hostname failed or has exited, so forwarding would produce a connection error the browser reports as a network fault. A successful resolve **touches** the preview: unlike `previews` (which the dashboard polls, so counting it would disable the reaper), a proxied request is somebody using the preview. |
| `preview_quest_run` | Run the anvil's E2E quests against a bead's live preview. Payload: `ipc.PreviewQuestRunPayload` — `bead_id` only (the preview names its own anvil). Answers synchronously with `ipc.PreviewQuestRunResponse`: `started` plus a `run_id` to poll, or `started=false` with a `reason` from the `ipc.PreviewQuestReject*` set (`not_enabled`, `not_healthy`, `no_preview`, `previews_disabled`, `already_running`, `no_entry_url`, `unavailable`). A refusal is an `ok` response, not an IPC error, so the web layer can map the two gate reasons onto `403`. The browser work runs on its own goroutine. |
| `preview_quest_status` | Read one quest run. Payload: `ipc.PreviewQuestStatusPayload` — `run_id` for a specific run, else `bead_id` for that bead's most recent one. Answers `ipc.PreviewQuestStatusResponse`; a bead that never ran quests is `found=false`, not an error. |

### Configuration

Config resolution order: `--config` flag → `./forge.yaml` → `~/.forge/config.yaml`. Environment variables override with `FORGE_` prefix (e.g. `FORGE_SETTINGS_MAX_TOTAL_SMITHS=4`). The daemon hot-reloads the config file on change via fsnotify. See [docs/configuration.md](docs/configuration.md) for the full settings reference including `daily_cost_limit`, `max_ci_fix_attempts`, `max_review_fix_attempts`, `max_rebase_attempts`, `stage_providers`, `merge_strategy`, `schematic_enabled`, `depcheck_interval`, per-anvil `hooks`, `smith.deny_patterns`, `temper` commands/steps, and more.

### Per-Anvil Smith Prompt Customization

Place a template file at `<anvil-path>/.forge/prompt.tmpl` or `.forge/smith-prompt.tmpl` to override the default Smith prompt for that repo. The template receives `{{.Bead}}`, `{{.AgentsMD}}`, `{{.ClaudeMD}}`, `{{.ReadmeMD}}`.
