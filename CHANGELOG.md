# Changelog

All notable changes to The Forge will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

Unreleased changes live as fragments in `changelog.d/` and are assembled at
release time by `scripts/assemble-changelog.sh`.

## [0.28.0] - 2026-09-01

### Added

- **Assay bounds re-measured under the reading prompts** - The R2 sample Forge-sra6 could not take: 13 runs / 78 pass observations / 95 pass sessions past the reading-prompt boundary, appended to `docs/assay-turn-budget.md` as a dated section with the earlier ones left byte-identical. The window turned out to hold Forge-sra6's own $1.50 → $3.00 ceiling raise, so it is partitioned into R2 and R3 rather than blending a ceiling against itself. The $3.00 ceiling is now non-binding (zero `error_max_cost` in 12 runs / 88 sessions, p90 at 47% of it and max at 61%, against R1's max at 98%) and the raise was load-bearing rather than precautionary — 8 of 88 sessions came in above $1.50, across all five deep passes, and the one run that met the reading prompts under the old ceiling lost its conventions pass at $1.53. The 16-turn cap is now the binding bound and the two are no longer adjacent: it ended 16 of 76 deep sessions (21.1%, against R1's 10.2% over its own 118 deep sessions — twice the rate, compared like for like rather than against R1's diluted all-session 8.5%), holding $1.15 mean / $1.84 max against $3.00. The reading prompts worked — the first `tools=` observation there has ever been, 58 of 60 first attempts calling a tool and security on 12 of 12, at ~2.8x a non-reading session, which is +7% at the run level. `files=` is structurally 0 and says nothing, since all 742 tool calls are Bash and name no `file_path` (filed as Forge-72oy, which also leaves the retry's diff-scoping modification never constructed). No setting is changed here; the turn-cap raise is filed as Forge-55eq, blocked on that. (Forge-cikv)
- **Per-pass cost in Assay telemetry** - The daemon's Assay `passes=` log line now carries `cost_usd=` (what the provider billed) and `cost_est=` (costTracker's running estimate) for each pass. `assay.max_cost_per_pass_usd` is compared against the estimate, never the billed total — the two differ by a structural ~1.61x — so the ceiling can now be sized from the log instead of by reproducing the tracker by hand over raw session logs, which could never see the sessions the ceiling actually killed. Each field is omitted rather than rendered as a zero where nothing measured it. (Forge-6ltv)
- **`measurements/` extracts behind the Assay turn-budget re-measurement** - The two JSON extracts `docs/assay-turn-budget.md`'s "Re-measurement — 2026-08-29" section is computed from, committed before analysis so its per-session cost and per-pass turn figures are reproducible from the repository rather than from a `daemon.log` that stood at 97% of its rotation threshold when they were taken. The `error_max_cost` crossings are the one class of figure that stays log-only, by construction: a cost-killed session emits no `result` event, so it cannot appear in a session extract at all. Both recorded extractors ran verbatim and clean, which is itself a result: the `passes=` field and the session-log event shapes have not drifted, so the R1 figures and these are the same measurement. (Forge-cikv)

### Changed

- **Assay per-pass spend ceiling raised from $1.50 to $3.00** - Re-measuring the bound found it had stopped being a runaway brake and become a clip point. Across the 141 pass sessions logged under the corrected turn counter, the largest surviving in-flight estimate was $1.467 — 98% of the ceiling — and the four sessions that crossed it crossed at $1.51-$1.58, taking four of one run's five deep passes out on `error_max_cost`, which is terminal and never retried (PR #872 came back "partial: 1 of 5 passes completed"). The new value clears that censoring point by a factor rather than being read off a percentile of a distribution the ceiling itself truncates, and still catches an order-of-magnitude runaway: $3.00 estimated is about $4.80 billed, over four times the mean billed session in that sample. Note the ceiling is compared against Assay's own input/cache-priced estimate, which runs roughly 1.6x under the provider's final figure — set `assay.max_cost_per_pass_usd` in that unit. `docs/assay-turn-budget.md` has the distribution and the derivation. (Forge-sra6)
- **Assay turn budget left at 16** - Its trigger did not fire: no pass ended `error_max_turns` in the measured window, 12 of 141 sessions reached the 16-turn cap and every one recovered on its modified retry, and the security pass never reached it at all. Raising the cap first would also convert recoverable turn exhaustions into terminal spend stops, since sessions now arrive at the turn cap holding $0.85-$1.45 of the per-pass budget. (Forge-sra6)

(Forge-x8yo)

TypeScript is a full application language, not just a styling surface, and the ext-682 warden batch re-scoped its frontend rules to `**/*.ts`/`**/*.tsx`, which left three of them inert: `markdown-image-render-untrusted` (security), `split-on-collapsed-preview` (performance) and `date-parse-fallback` (error-handling). `.ts`/`.tsx` now map to all canonical categories; `.css` stays `{ui, style, other}`, since a stylesheet really is a styling surface only, and `*_test.tsx` still resolves to `{testing, other}` through the early return above the switch. (Forge-y0g2)

### Fixed

- **A batch merge never reclassifies a `security` rule out of review scope** - The intra-batch pass clusters across categories and gives the merged rule the cluster's dominant one, but a rule's category is a review-time gate: a `.cs` diff selects `security` and excludes `testing`. One `security` rule merged into two near-duplicate `testing` ones would silently stop being reviewed on the next .NET diff. Such a cluster is now split at the boundary instead, so both sides keep landing where they landed before — and each side is re-clustered afterwards, since clustering is transitive and removing the security member can remove the only edge that held the rest together. (Forge-aszm)
- **Assay `files=` telemetry and retry diff scoping** - The Assay pass tracker recorded a file only from a `file_path`-shaped tool input, but measured over 95 pass sessions every one of 742 tool calls was `Bash` — so `files=` was 0 on every logged pass and the turn-budget retry's third modification (the diff scoped to the files the failed session opened) was never constructed. Paths are now also read from shell command lines (including git's `<rev>:<path>` form, input redirection and a quoted `sh -c` sub-command) and from the `path`/`notebook_path` input keys; `files=` counts only the names that look like a file, so a directory argument cannot report a pass that opened nothing as having read code, and only files already in the diff can be selected for a retry's scope — a bare basename matching two of them narrows nothing rather than pointing at the wrong package. (Forge-72oy)
- **Burnish stops re-fixing review comments it has already addressed** - A review thread carries its handled state on the platform, so `GetReviewComments` drops resolved threads and that half of the actionable set drains as Burnish resolves them. A review-level or PR-level comment belongs to no thread and can never be resolved, and nothing distinguished one Burnish had already worked through from one that had just arrived — so every Copilot review body, every Assay summary and every bot comment on a PR stayed permanently actionable and was re-sent to the model on every round, for the life of the PR. Munin#5423 measured that residue growing 3 → 4 → 5 → 6 across four rounds while the resolvable thread count fell 9 → 4 → 1: round 3's Assay returned `findings=0`, but five stale summaries kept Burnish running, and the change it made with nothing real to do is what produced round 4's two findings. Non-thread comments are now recorded as handled after a successful fix and push — the equivalent of `ResolveThread` for comments that have no thread — and filtered out of later rounds. Identity includes a hash of the body, so editing a comment to add a new request re-surfaces it rather than leaving it suppressed under an ID that was already recorded; a comment with no stable ID is never recorded and stays actionable; and thread comments are deliberately left to resolution, since dropping one here would hide a thread the platform still shows as unresolved.
- **Contradictory learned rules are surfaced instead of shipped silently** - Rules from one source PR that prescribe opposite orderings — a callback invoked under the lock versus after releasing it, persist-then-clear versus clear-then-persist — are reported in the batch PR's commit message and body, in the daemon log and by `forge warden consolidate`. They are never merged or dropped: which convention a codebase wants is a human decision. (Forge-aszm)
- **Contradictory rule pairs are announced once, not on every flush** - The scan runs over the whole rules file and a pair is only ever cleared by a human, so every flush re-emitted every pair ever found into the log and the activity feed. Each pair is now reported once per anvil; the batch PR still lists them all. (Forge-aszm)
- **Learned rule IDs are sanitized before reaching a published PR body** - A rule's ID is whatever the distillation model returned and nothing validates a character of it, so a backtick, a newline or an `@org/team` in one would have broken out of its code span, forged further sections or mass-notified a team in a PR body posted under Forge's own GitHub identity. IDs, source references and categories now render through a closed alphabet, in the batch commit message as well as the PR body — a forged `Closes #123` or `Co-authored-by:` line in a commit Forge authors onto the default branch is the same exposure. (Forge-aszm)
- **Near-duplicate rules are detected by containment as well as Jaccard** - Jaccard cannot score a terse restatement of a verbose rule above `|short|/|long|`, which is why the shipped `dedup_threshold` of 0.6 clustered nothing at all across 727 real rules. A second criterion, `settings.warden.overlap_threshold` (default 0.55), measures how much of the shorter rule's vocabulary the longer one already contains; either criterion firing makes a pair a duplicate. (Forge-aszm)
- **Rule consolidation identifies cluster members by position, not by ID** - Where a rules file held two rules under one ID, merging a cluster removed both while archiving only the one the cluster contained — a rule of coverage deleted with no archive entry and nothing in the log. Both passes now remove exactly the rules they merged, and the intra-batch pass excludes a colliding ID and reports it rather than guessing which rule it was handed. (Forge-aszm)
- **Rule consolidation is switched off with a negative `dedup_threshold`** - The off switch was documented as `0`, which could never reach the daemon: `0` is the setting's zero value, so an unset config and an explicit `dedup_threshold: 0` both resolved to the default of 0.6 and consolidation could not be turned off at all. A negative value now disables both passes, matching how `archive_after_days` already reads its own disable. (Forge-aszm)
- **Smelter dedupes a warden-rule batch against itself before committing** - A batch is now clustered and consolidated across categories before it is measured against the rest of the rules file, so one check learned eight ways ships as one rule instead of eight copies in every Warden prompt. The old pass grouped by category first, and a learned rule's category is whichever the distillation session picked, so a cluster spread over `style`/`documentation`/`other` was invisible to it. (Forge-aszm)
- **Smelter paths backfill is rule-aware** - Backfilled Warden rule `paths` are now derived from the language the rule's own pattern/check text names, intersected with the extensions the source PR touched, instead of every extension the PR happened to include. A Go rule learned from a mixed Go+frontend PR no longer carries `**/*.ts`/`**/*.md`, which had made the path-glob filter stop narrowing anything. The language signals are language-unique tokens only — bare prose words (`nil`, `defer`, `chan`, `props`) are not signals, since they attribute language-agnostic rules to Go — and an inference the source PR's own files contradict is discarded in favour of those files, so a misfire can never leave a rule gated on a language its diffs never contain. A directory glob (`changelog.d/**`) is additive to the PR-derived set rather than a replacement for it, and is kept only when the source PR actually touched a file it matches. Rules whose text names no language keep the old PR-derived set. (Forge-w0f6)
- **Temper detects .NET projects at any depth** - Detection asked `filepath.Glob` for `**/*.csproj`, which matches only one directory level, so a repository laid out as `src/Api/Api.csproj` with no root solution was not detected as .NET at all and fell through to the "No build system detected" step, verifying nothing. The worktree is now walked (bounded depth, skipping build output and dependency trees); the entry point is the shallowest solution, else every discovered project in its own build step, each named on the `dotnet` command line unless it is the single target in the worktree root. Only projects carrying a test runner get a `test` step, and an explicit `<IsTestProject>` overrides that either way. (Forge-2qtu)
- **The per-PR Assay run cap is enforced on the Burnish coordination path** - `assay.max_runs` exists so the Assay → Burnish → new-head loop terminates, and Bellows stops re-firing at the cap; `ensureAssayReviewedHead` is reached from the Burnish worker instead and checked enabled/shadow/head-SHA but never the cap, so it bypassed the termination condition entirely. Munin#5423 logged `run cap reached (2/2)` and then `(3/2)` from Bellows while Assay ran a third and fourth time from this path — each run blocking the fix it is meant to inform, since the call is synchronous, and each reviewing a diff the previous round's fix had just enlarged. The gate now mirrors `shouldEmitReviewNeeded`: `>=` rather than `==`, since the count can already exceed the cap when this path runs, and `max_runs <= 0` still means no cap.
- **Two learned rules sharing an ID are both kept** - A rule's ID is written by whichever distillation session produced it, so two comments on one PR routinely arrive named the same thing; the second was dropped from the pending queue by an ID check with nothing said about it — and it was exactly the restatement the new intra-batch pass exists to merge into the first. It is now stored under a suffixed ID, so both reach the file, cluster, and commit as one rule. Re-learning a rule already on file is still a no-op. (Forge-aszm)
- **`warden.dedup_threshold` and `warden.archive_after_days` edits now hot-reload** - Both are resolved through a closure at flush time so an edit takes effect without a restart, but the config watcher did not detect either, so the closure kept reading the old value. (Forge-aszm)
- **`warden.overlap_threshold` edits hot-reload too** - Added alongside the `dedup_threshold` and `archive_after_days` watcher entries, with tests: a setting missing from the watcher is inert in a way nothing errors or logs about. (Forge-aszm)

## [0.27.1] - 2026-08-27

### Changed

- **Blocked dependency scans escalate once instead of failing nightly** - Depcheck now classifies a git failure as transient (DNS, timeouts, connectivity, credentials) or blocked (detached HEAD with no upstream, a ref the fetch cannot lock, a tree left mid-merge). A transient failure keeps its per-run `depcheck_failed` event and is retried next run; a blocked one is announced once, raises an anvil-level Needs Attention entry naming the checkout and git's own words, and stays silent until the condition changes — then clears itself on the next scan that reads the anvil's manifests. (Forge-4v1w)
- **Depcheck blocked-scan escalations say what to do** - A blocked dependency scan no longer reports git's raw stderr as its headline. The Needs Attention entry now names the anvil and its checkout, enumerates the blocking paths from `git status` — annotating the pod-local `.beads/config.yaml` and bd-regenerated `.beads/.gitignore` so an operator recognises them as expected rather than as the problem — and gives the single recoverable command that resolves the condition — bounded honestly, so where more paths are blocking than fit one readable command the line says it sets the first five aside and points at `git status` for the rest, rather than reading as the whole fix. git's own output is kept as the trailing `git output:` evidence. Which condition is escalated, and when it is suppressed, is unchanged. The blocking paths are read from `git status --porcelain -z`, so a filename containing ` -> ` or a space is reported and stashed as itself rather than cut into a path that is not in the tree; a scan whose paths could not be enumerated says so instead of claiming nothing unexpected is modified; the `not a git repository` remedy pairs `forge anvil remove` with the add, which alone would be refused as a duplicate; and the whole entry is budgeted against the same `maxFailureDetailBytes` bound the git evidence inside it already respected. (Forge-0uvl)
- **Depcheck git failure reporting hardened** - A git command killed by its deadline now carries that deadline as a cause, so a timed-out fetch classifies as transient instead of unmodelled; both reporting exits strip and bound git's own words before they reach the log and the activity feed; the Needs Attention headline is rendered by the record rather than written in two packages; and the on-demand scan path gets the same 1-minute timeout floor the scheduled one has, instead of running every ecosystem scan against an expired deadline. (Forge-4v1w)

### Fixed

- **A bare `<2.0.0` npm range no longer swallows a real major update** - Such a range excludes the version it names, but it normalized to that version and made the update read as already applied upstream. (Forge-wfd2)
- **A checkout-blocked self-deploy is always escalated** - A pull stopped by a merge Forge itself detected now raises its Needs Attention entry on that detection rather than on whether git's wording matches a known pattern. Previously a refusal phrased in an unmodelled way — or a fast-forward git did not refuse at all — was recorded as an ordinary failure and retried silently on every merge, leaving the daemon on its old binary with the evidence only in the event log. (Forge-0ki2)
- **A mid-merge checkout is never stashed** - A self-deploy whose checkout is part-way through a merge, cherry-pick or revert no longer sets that state aside to pull over it. Both shapes are caught: conflicts still unresolved in the index, and conflicts already staged with `git add` — where the index looks clean and only `MERGE_HEAD` says the merge is unfinished, so every git stashed it happily and the reset that performs deleted `MERGE_HEAD`, quietly turning the operator's merge into a one-parent diff. The pull is attempted as the tree stands, git's own refusal is what the Needs Attention entry quotes, and the half-finished merge is left exactly where they left it. (Forge-0ki2)
- **A project missing from the checkout is logged, not silently skipped** - The npm guard now stats the `package.json` rather than its directory (a manifest upstream added inside an existing directory made npm walk up and report the parent project's packages as this one's), and both ecosystems log each skip plus the case where no project was scannable at all — previously indistinguishable from "all dependencies up to date". (Forge-wfd2)
- **A repo-root solution no longer reconciles repo-wide** - A `.sln`'s pin scope is the directories of the projects it references, read out of the solution file, rather than its own directory tree — which at the repository root is the whole repository, so a project the solution does not even reference could silence a real update inside it. A project's scope is likewise its own directory rather than its subtree, since MSBuild's import walk only goes up and a root-level project's subtree is the whole repository again. Such an out-of-scope project is now scanned in its own right, and F#/VB projects are scanned as well as read. (Forge-wfd2)
- **A retained stash keeps its Needs Attention entry** - When a self-deploy leaves local changes in a stash it could not restore, the entry is no longer withdrawn by the next deploy that pulls successfully — the recovery leaves the checkout clean, so that would reliably delete the only record of where the work went. It is withdrawn once the stash stack no longer holds a `forge-selfdeploy` entry, and the message says so. (Forge-0ki2)
- **A solution that cannot be read is no longer given its tree** - A missing or unreadable `.sln` blob used to be indistinguishable from one naming no project, and took the whole-tree fallback — at the repository root, repo-wide reconciliation again. It is now dropped as a scan target so its projects are each scanned with their own scope, and both cases are logged rather than passing in silence. (Forge-wfd2)
- **Assay prompts frame tool-read files as untrusted** - The shared prompt preamble enumerated the prompt's own sections as untrusted data and stopped there, which left file content pulled in mid-session through tools arriving as ordinary context — in a checkout of the contributor's own head, in sessions now explicitly told to go and read it. It now says the same of everything a pass opens with its tools, elided files included: content to review, never instruction — and the one carve-out, the trusted "Repository Review Guidance" block, is scoped explicitly to that SECTION OF THE PROMPT rather than to the filename, since the guidance is read from the anvil's own checkout while the pass session's working directory is the contributor's head, where `REVIEW.md` is an ordinary tracked file the pull request may rewrite. (Forge-q2qz)
- **Assay security and repo-specific passes now read the code, not only the diff** - `security.md` closed with "Do not speculate about code you cannot see", which was written against hallucination and read as an instruction not to open files: the pass averaged 2.5 turns and ended within two turns — i.e. without a single tool call — on 13 of the 20 most recent runs, missing the authorization and concurrency defects that are only visible one hop off the diff. The clause now constrains what may be claimed rather than what may be read, and the pass is told to follow the call path: read the whole of every changed file, read the callers, read a sibling endpoint for the canonical permission pattern, and establish a service's lifetime and callers before judging shared state. `repo_specific.md` gets the matching minimum-exploration instruction — work the repository guidance as a checklist and verify each applicable item against the file it concerns — after ending at exactly one turn on a third of runs. Both passes are still bounded by `assay.max_cost_per_pass_usd`. (Forge-q2qz)
- **Blocked self-deploys escalate instead of deferring quietly** - A pull refused by the checkout's own state (a tree left mid-merge, a detached HEAD, an unlockable ref) reproduces identically on every merge, so it now raises a Needs Attention entry naming the blocking paths and the one command that resolves it, withdrawn by the first deploy that pulls successfully. Transient failures (network, credentials) still just retry. (Forge-0ki2)
- **Depcheck no longer needs a clean anvil working tree** - The dependency scan now fetches the checkout's upstream tracking branch and reads `go.mod`, `*.csproj` and `package.json` out of that ref's blobs instead of running `git pull --ff-only` first. A pull is refused whenever a tracked file has local modifications the incoming commits touch, so an anvil that must carry a permanent local edit (a pod-local `.beads/config.yaml`, bd's own additions to `.beads/.gitignore`) was skipped on that run and on every run after it. A fetch writes only to `.git`, so such an anvil is now scanned normally and its local modifications are intact afterwards. The staleness the pull guarded against is handled from the data instead: an update the tracking ref already pins at the latest version is no longer reported, so a merged-but-unpulled bump does not file a duplicate bead. (Forge-wfd2)
- **Depcheck reads the branch's real upstream** - The tracking ref comes from the checked-out branch's own `@{upstream}`, falling back to the same branch name on `origin`, rather than assuming `origin/main`. (Forge-wfd2)
- **Depcheck tells a missing manifest from a failed git** - Whether a path exists at the tracking ref is now decided by `git cat-file`'s exit code rather than by matching git's `fatal:` text, which is translated: on a non-English host every scheduled scan of a .NET- or Node-only anvil reported a Go manifest-read failure and wrote a `depcheck_failed` event, forever. (Forge-wfd2)
- **Dependency reconciliation is scoped per project** - An update is only checked against the manifests that apply to the project it was reported for. Folding every `package.json` or `.csproj` in a repository into one map let a monorepo project that upstream had already upgraded silence the same, still-real update in its siblings. Central `Directory.Packages.props`/`Directory.Build.props` in ancestor directories still apply, as MSBuild itself applies them. (Forge-wfd2)
- **NuGet version ranges are no longer read as pins** - A `PackageReference` pinned with NuGet's bracket syntax (`[1.2.3]`), an interval (`[1.0.0,2.0.0)`) or a float (`1.0.*`) was recorded verbatim, so a bracket-pinned patch bump was rewritten to `[1.2.3] → 1.2.4` and re-classified `major` (routing it to needs-attention instead of auto-dispatch), and an update upstream had already merged was never dropped. A bracket pin is now read as the exact version it is, and an interval or float pins nothing, so the package is passed through untouched. (Forge-wfd2)
- **Per-pass tool-call telemetry** - The daemon's Assay log line now carries `tools=<calls> files=<distinct paths>` per pass alongside `turns=`: tool calls summed over the pass's sessions, files as the deduplicated union of what they opened. Turns is a weak proxy for the only coverage question that matters — whether a pass read any code at all — and `tools=0` says it outright, so it is rendered wherever it can be told apart from a missing measurement (any pass on the same PROVIDER reporting a count proves that backend reports them; where none does, that backend's passes omit the fields rather than print ambiguous zeros). The gate is per provider and not per run because a run is not one provider — `assay.triage_provider` is resolved independently of `review_provider`, so triage on Claude beside deep passes on Copilot would otherwise have printed `tools=0` for five passes that were never measured at all. A backend that reports its tool calls in its result event rather than per message (Gemini) falls back to that figure instead of reporting nothing. (Forge-q2qz)
- **Self-deploy survives a dirty Forge checkout** - A stray local edit in Forge's own repository used to refuse `git pull --ff-only` on every self-deploy from then on, so the running daemon silently fell behind main. The pull now sets the working tree aside in a named stash and puts it back, verifying the entry was actually consumed; a restore that conflicts aborts the deploy with the stash ref, the conflicting paths and a recovery command instead of rebuilding over the work. (Forge-0ki2)

## [0.27.0] - 2026-08-25

### Added

- **Assay prompt-cache accounting on the run record** - Each Assay run now records the prompt-cache tokens its sessions wrote and read (`assay_runs.cache_creation_tokens` / `cache_read_tokens`, added by migration and defaulting to 0 on existing rows), on the failed path as well as the successful one — a run that died was still billed for the prefixes it wrote. The daemon's `Assay review completed` line carries the same totals as `cache_w` / `cache_r` plus `cache_w_redundant`, the write tokens a run paid for more than once, so a lost shared prefix is visible in a log line and a trend across a PR's runs is a query. (Forge-7a72)
- **Assay repeat-review cost attribution** - New `forge cost assay` command reports Assay spend split by first-review vs re-review of a PR and by cache-write/cache-read token class, in table, JSON or CSV form. Run ordinals are derived over each PR's full review history before the reporting window is applied, so a repeat review whose first review predates the window is not miscounted as a first. Runs recorded before prompt-cache instrumentation report token class `unknown` rather than a misleading zero. (Forge-477m)
- **Per-pass USD ceiling for Assay reviews** - A review pass session now carries a spend ceiling (`assay.max_cost_per_pass_usd`, default $1.50, `0` disables). ### Security

- **Proxied Kiln previews are behind the Hearth session** - With `settings.preview_proxy_base` set, a request arriving on a preview hostname now has to come from a signed-in Hearth operator.
